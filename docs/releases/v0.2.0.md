# devkit v0.2.0 — review once per task

The `review` module now costs one `code-review` run per task, two when the first found defects,
instead of one per hand-back. The commit gate stays and still fails closed. The reasoning is in
[ADR-0001](../adr/0001-review-once-per-task.md).

## What changed

- **Rule text** (`## Review` in `CLAUDE.md`). Review runs once, when a task's implementation is
  finished, not at each hand-back or follow-up. A second run happens only to verify the fixes for
  defects the first one found, and there is never a third. Branch review before a pull request runs
  only when the branch has commits that no task review saw: work from another tool or agent, or
  from someone else.
- **Reviewer** (`.claude/agents/code-review.md`).
  - Every finding has a kind. A **defect** is wrong behaviour, with the input and the wrong outcome
    stated. A **cleanup** is a broken rule whose fix leaves behaviour unchanged: naming, structure,
    logging, style, a missing test. A **note** never blocks.
  - Round 1 reports every defect and cleanup at once, numbered, with `file:line` and the fix it
    needs.
  - Round 2 runs only after defects and checks only their fixes. It reports new defects only for an
    unfixed one, one the fixes introduced, or a `critical` finding with an exploitation scenario.
  - The reviewer uses the check results the caller passes in, and no longer re-runs the full suite
    itself.
  - The reviewer records its tree in every round, adding `--blocking` when it found a defect, and
    `--file <path>` for each file outside the slice that a cleanup needs, such as a new test.
- **Commit gate.** Besides the exact approved tree, the gate now passes:
  - a fix of up to `smallFix.maxLines` lines (150 by default) on top of an approval, to files the
    review covered or named, measured against the approved tree. This is how cleanups and later
    tweaks land without another run. Over a tree recorded with defects, no code change passes until
    round 2 approves;
  - a commit that only touches docs: text files with mode `100644`, matching `docs.include` and not
    `docs.exclude`.

  Dependency manifests, lockfiles, registry and publish config (`alwaysReview`), `CLAUDE.md`,
  `.mcp.json`, and any `.claude/` directory always need a review, however small the change. A
  submodule bump counts even when git is configured to hide it from diffs.
- **New file `.claude/review.json`.** It holds the limit and the globs above. The gate reads it as
  committed at `HEAD`. If it is missing or invalid, nothing is exempt.
- **New hook files** under `.claude/hooks/`: `path-glob.mjs`, `diff-entries.mjs`,
  `approval-record.mjs`, `review-config.mjs`, and `review-exemptions.mjs`.

## Upgrading a project that vendors devkit (e.g. RAID on 0.1.12)

1. Run the `init` skill to upgrade. It replaces the `review` section of `CLAUDE.md`, the agent, and
   the hooks, and creates `.claude/review.json`. If you kept a local override of `code-review.md`,
   merge its new **Checks**, **Findings**, **Rounds** and **Verdict** sections into it by hand;
   otherwise the old reviewer treats cleanups as blocking, and every cleanup costs a second round.
   If you kept one of `review-gate.mjs`, `git-state.mjs` or `approve-review.mjs`, start again from
   the new file: the gate's exemptions and the approval record live there.
2. Edit `.claude/review.json` for the project:
   - Add every directory where a `.md` file is read by the program, such as prompt files, to
     `docs.exclude`. `src/**` is already there.
   - Add any dependency files of your stack that are missing from `alwaysReview`.
3. Commit the upgrade. It touches `.claude/` and `CLAUDE.md`, so it needs one review. The
   exemptions start working once `.claude/review.json` is committed.
4. An approval recorded by an earlier release still matches its exact tree. It lists no files, so
   it allows no small fixes: the first change after the upgrade needs a fresh review.
5. If a project wrote its own review policy into `CLAUDE.md` to work around the old rule, compare it
   with the new `review` section and drop whichever duplicates the other.
